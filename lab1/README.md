# Лабораторная работа №1. Dockerfile

## Сервис

`dataset-profiler` — небольшой HTTP-сервис, который считает описательные статистики по CSV. Файлы не копируются в образ: каталог с датасетами монтируется в `/data`. Volume здесь обязателен, а сами данные можно заменить без пересборки.

Сервис выбран так, чтобы его можно было наращивать в следующих работах:

- Эта работа: один контейнер приложения и volume с CSV.
- Лабораторная 2: этот же `Dockerfile` в Docker Compose, рядом PostgreSQL и одноразовый init-сервис, который создаёт схему. Результаты профилирования будут сохраняться в базу.
- Лабораторная 3: отдельное упражнение по объектам Kubernetes на примере из методички.
- Лабораторная 4: тот же набор (приложение, init, база) в Kubernetes: свои Deployment, Service, ConfigMap/Secret, пробы и volume.

Стек: Python, FastAPI, pandas.

Эндпоинты:

- `GET /health` — процесс жив. Токен не требуется, чтобы на этот путь позже повесить пробу.
- `GET /datasets` — имена `*.csv` в каталоге `DATA_DIR` (по умолчанию `/data`).
- `GET /datasets/{name}/profile` — число строк и статистики по колонкам.
- `GET /docs` — интерактивная схема API.

Если в окружении процесса задан `PROFILER_TOKEN`, запросы к `/datasets` и `/profile` требуют заголовок `Authorization: Bearer <token>`. В хорошем образе эта переменная при сборке не задаётся, поэтому локальный запуск обходится без токена.

## Состав каталога `lab1/`

- `Dockerfile` — хороший образ. Его дальше берём в Compose и Kubernetes.
- `Dockerfile.bad` — образ, который запускается, но собран с антипаттернами.
- `app/main.py` — код сервиса.
- `requirements.txt` — зафиксированные версии зависимостей хорошего образа.
- `data/` — CSV для монтирования. В контекст сборки они не входят.
- `.dockerignore` — в контекст не попадают отчёт, PDF, датасеты и кэш Python.

Примеры датасетов: `data/experiment_runs.csv` и `data/sensor_readings.csv`.

## Сборка

Команды запускать из каталога `lab1/`.

```bash
docker build -f Dockerfile.bad -t dataset-profiler:bad .
docker build -f Dockerfile -t dataset-profiler:good .
```

## Запуск

Оба образа нужно запускать с монтированием `data`. Без `-v` процесс поднимется, а список датасетов будет пустым: CSV лежат на хосте, не в слое образа.

Плохой образ. Токен записан в образ при сборке, значение разобрано в разделе про практики.

```bash
docker run --rm --name profiler-bad -p 8000:8000 \
  -v "$(pwd)/data:/data:ro" \
  dataset-profiler:bad
```

```bash
curl -sS http://127.0.0.1:8000/health

curl -sS \
  -H "Authorization: Bearer lab1-do-not-use-this-token" \
  http://127.0.0.1:8000/datasets

curl -sS \
  -H "Authorization: Bearer lab1-do-not-use-this-token" \
  http://127.0.0.1:8000/datasets/experiment_runs.csv/profile
```

Хороший образ.

```bash
docker run --rm --name profiler-good -p 8000:8000 \
  -v "$(pwd)/data:/data:ro" \
  dataset-profiler:good
```

```bash
curl -sS http://127.0.0.1:8000/health
curl -sS http://127.0.0.1:8000/datasets
curl -sS http://127.0.0.1:8000/datasets/sensor_readings.csv/profile
```

Если хороший контейнер не читает файлы, каталог и CSV должны быть доступны на чтение пользователю `appuser` (uid 1000):

```bash
chmod a+rX data data/*.csv
```

Остановка: `docker stop profiler-bad` или `docker stop profiler-good`. В примерах занят один и тот же порт 8000, поэтому одновременно их не запускаем. Второй экземпляр можно опубликовать как `-p 8001:8000`.

Секрет из плохого образа виден без входа в контейнер:

```bash
docker image inspect dataset-profiler:bad --format '{{range .Config.Env}}{{println .}}{{end}}'
docker history dataset-profiler:bad
```

У хорошего образа строки `PROFILER_TOKEN` в этом выводе нет. Если токен нужен, его передают при запуске, например `-e PROFILER_TOKEN=...`. В Kubernetes для этого будет Secret, а не слой образа.

## Плохие практики в `Dockerfile.bad` и как они закрыты в `Dockerfile`

### 1. Незакреплённый базовый образ `python:latest`

Тег `latest` со временем указывает на другой Python и другой набор системных пакетов. Один и тот же Dockerfile сегодня и через месяц собирает разные образы, а сборка может внезапно сломаться.

В хорошем Dockerfile базовый образ зафиксирован дайджестом манифест-листа:

`python:3.12-slim-bookworm@sha256:935c3c5b12357a7e10caa9c1e6ca5692344d97cf229832ef584be2cec9fc03df`

Дайджест относится к multi-arch индексу (в том числе `linux/amd64` и `linux/arm64`), поэтому на другой архитектуре подтянется соответствующий вариант, а не чужой бинарь. Зафиксированы линейка Python 3.12 и Debian bookworm. Образ `slim` не включает компиляторы и документацию. Alpine сознательно не используется: колёса pandas и numpy собраны под glibc, на musl их пришлось бы компилировать внутри образа.

### 2. `apt-get upgrade`, лишние пакеты и отдельные слои без очистки кэша

В плохом файле три отдельные инструкции: `apt-get update`, затем `upgrade`, затем установка `vim`, `curl` и `build-essential`. Для HTTP-сервиса они не нужны.

Почему это плохо:

- `upgrade` делает сборку недетерминированной: в образ попадает то, что в день сборки лежит на зеркале Debian.
- `update` и установка в разных слоях. Списки пакетов остаются в слое `update`: удаление кэша следующей командой не уменьшает уже записанный слой.
- Отдельный слой `update` ещё и устаревает. При пересборке Docker может взять его из кэша, а зеркало к этому моменту уже убрало старые индексы, и `install` падает.
- Редактор, curl и компилятор увеличивают размер и число потенциальных уязвимостей. Если процесс в контейнере скомпрометируют, этими утилитами проще развивать атаку.

В хорошем Dockerfile системные пакеты не ставятся. Зависимости Python ставятся готовыми колёсами. Образ меньше, поверхность атаки уже.

### 3. Секрет записан в образ через `ENV`

`ENV PROFILER_TOKEN=lab1-do-not-use-this-token` попадает в конфигурацию образа и в историю слоёв. Токен видит любой, у кого есть образ: `docker image inspect` и `docker history`. Смена токена требует пересборки, а старое значение остаётся в предыдущих слоях и в уже выданных образах.

В хорошем Dockerfile этой переменной нет. Код читает `PROFILER_TOKEN` из окружения уже запущенного процесса. Для локальной работы переменную можно не задавать. Если её передают, то при `docker run -e` или через секрет оркестратора, а не при `docker build`.

### 4. Сначала копируется весь контекст, зависимости не закреплены

`COPY . /app`, и только потом `pip install fastapi uvicorn pandas`.

Почему это плохо:

- Слой с зависимостями зависит от любого файла контекста. Правка `main.py` заставляет заново скачивать numpy и pandas.
- Без версий `pip` ставит то, что в день сборки считается последним. Повторная сборка может получить несовместимый релиз.
- Кэш pip остаётся в слое, потому что нет `--no-cache-dir`.
- В один слой попадает весь оставшийся контекст, а не только код приложения.

В хорошем Dockerfile сначала копируется только `requirements.txt`, затем выполняется `pip install --no-cache-dir -r requirements.txt`. Версии закреплены через `==`. Каталог `app` копируется следующим шагом. Пока зависимости не менялись, Docker берёт слой `pip` из кэша. `.dockerignore` не отправляет в контекст PDF, отчёт, каталог `data` и кэш Python: датасеты приезжают volume, а не слоем образа.

### 5. Процесс от root, каталог приложения доступен на запись всем

`chmod -R 777 /app` и отсутствие `USER`. Процесс получает права root внутри контейнера, а код приложения может изменить любой пользователь контейнера. Изоляция namespace сама по себе не закрывает монтирование сокета Docker или широкого каталога хоста: в таком запуске root в контейнере становится путём к хосту. Это отдельно разобрано ниже, в практиках использования.

В хорошем Dockerfile создаётся пользователь `appuser` с uid 1000, каталог `/app` передаётся ему, процесс переключается инструкцией `USER`. Права 777 не выставляются. Порт 8000 больше 1024, поэтому непривилегированный пользователь может его слушать.

### 6. Shell-форма `CMD`

Инструкция `CMD python -m uvicorn ...` выполняется как `/bin/sh -c "python ..."`. PID 1 — оболочка. Она не передаёт приложению `SIGTERM`, поэтому `docker stop` часто ждёт таймаут и добивает процесс через `SIGKILL`.

В хорошем Dockerfile используется exec-форма:

```dockerfile
ENTRYPOINT ["python", "-m", "uvicorn"]
CMD ["app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Uvicorn становится PID 1 и получает сигнал остановки напрямую. Разделение `ENTRYPOINT` и `CMD` позволяет в Compose подменить аргументы, не переписывая образ.

В хорошем образе также заданы `PYTHONUNBUFFERED=1` и `PYTHONDONTWRITEBYTECODE=1`: логи сразу попадают в `docker logs`, а в файловой системе контейнера не появляются `.pyc`. Инструкция `VOLUME ["/data"]` фиксирует точку монтирования CSV. Она не подставляет каталог хоста сама: в `docker run` по-прежнему нужен `-v`.

## Две плохие практики использования этого контейнера

Образ при этом может быть уже хорошим. Ломается способ запуска.

1. Монтировать в `/data` домашний каталог или корень файловой системы (`-v "$HOME:/data"` или `-v /:/data`). Сервису нужен только каталог с CSV. Широкий volume отдаёт контейнеру чужие файлы, ключи и исходники. Ошибка в разборе пути или компрометация процесса заденет данные хоста. Нужен узкий каталог и, поскольку сервис только читает файлы, режим только для чтения: `-v "$(pwd)/data:/data:ro"`.

2. Запускать профилировщик с `--privileged` и сокетом демона (`-v /var/run/docker.sock:/var/run/docker.sock`), чтобы обойти права на файлы. Для чтения CSV это не нужно. `--privileged` снимает большую часть изоляции контейнера. Сокет Docker из контейнера позволяет создавать и удалять контейнеры, монтировать диски хоста и управлять машиной. Доступ к датасетам решается правами каталога и пользователем `appuser`, а не отключением защиты.

## Когда контейнеры использовать не стоит

1. Нужно другое ядро, чем у хоста, или свои модули ядра: часть драйверов и низкоуровневый системный софт, который нельзя безопасно пробросить устройством. Контейнер делит ядро с хостом. Здесь подходит виртуальная машина или установка на bare metal.

2. Нужна жёсткая изоляция недоверенного кода и отдельное ядро на границе безопасности. Namespace, cgroup и seccomp уменьшают доступ, но это не граница гипервизора: побег из контейнера эксплуатирует общее ядро. Для мультиарендности с сильными требованиями безопасности берут виртуальные машины или отдельные узлы.

## Результат сборки

Оба образа собираются. На проверке `dataset-profiler:bad` занял 1.44GB, `dataset-profiler:good` — 313MB.

`docker image inspect` показывает, что антипаттерны из `Dockerfile.bad` реально попали в образ, а в хорошем их нет:

- Плохой образ запускается от root (`User` пустой). `Cmd` имеет shell-форму: `/bin/sh -c "python -m uvicorn ..."`. В окружении образа лежит `PROFILER_TOKEN=lab1-do-not-use-this-token`. База `python:latest` на момент этой сборки оказалась Python 3.15.2.
- Хороший образ запускается как `appuser`. Команда в exec-форме: `ENTRYPOINT ["python","-m","uvicorn"]` и `CMD ["app.main:app","--host","0.0.0.0","--port","8000"]`. Переменной `PROFILER_TOKEN` нет. Зафиксированный дайджест разрешился в Python 3.12.16.

- В README разобраны практики обоих файлов.
- Запуск обоих образов требует volume с CSV.
- Отдельно описаны две плохие практики использования этого контейнера и два случая, когда контейнеры как инструмент не подходят.
